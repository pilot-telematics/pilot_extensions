# Совместимость API PILOT и границы поддержки

Этот справочник объясняет, как выбирать интерфейсы PILOT для расширения. Он отделяет документированные контракты от наблюдений runtime и настроек конкретной установки.

Дата проверки: 2026-11-02.

## Область совместимости

В [публичном руководстве PILOT](https://docs.pilot-gps.com/current/what_s_new_in_pilot_7_10.html) указана версия 7.10. В рабочей папке `Pilot7` также есть файлы выпуска 7.11. Эти файлы не подтверждают, какая версия работает у клиента. Перед использованием особенностей версии проверьте целевую сборку.

Эта проверка подтверждает сведения из опубликованных примечаний 7.10. Она не подтверждает каждую деталь runtime расширений на развёрнутой сборке 7.10.

В примечаниях 7.10 сказано, что AI-помощник PILOT может подсказывать разработчикам по API и созданию расширений. В них не описан новый runtime-контракт или API для расширений. Используйте руководства этого репозитория при разработке расширения, а поведение API сверяйте с актуальной спецификацией PILOT.

Репозиторий расширений описывает свои шаблоны интеграции. Он не определяет контракт каждой конечной точки API или настройки аккаунта PILOT.

## Уровни поддержки

Используйте эти метки в документации расширения и при проверке кода:

| Метка | Значение | Как использовать |
|---|---|---|
| Документированный API | Текущая спецификация PILOT описывает endpoint, поля и авторизацию. | Используйте как основной контракт интеграции. |
| Документированный runtime расширения | Этот репозиторий описывает host-объект или шаблон интеграции. | Проверяйте наличие необязательных классов и методов, если руководство допускает различия. |
| Legacy-интерфейс | Endpoint использует UI PILOT, но публичная спецификация API не определяет его для расширений. | Не используйте в новых интеграциях, пока PILOT не подтвердит поддержку и совместимость. |
| Наблюдение runtime | Поведение найдено в сборке или наблюдалось в одной установке. | Считайте это данными для конкретной версии. Не описывайте как стабильный контракт. |
| Политика установки | Настройка относится к серверу, аккаунту, proxy или WAF. | Уточните её у владельца установки. |

Успешный запрос или работающий пример не меняет уровень поддержки интерфейса.

## Выбор источника API

1. Используйте актуальную спецификацию PILOT API v3, если она описывает нужную операцию.
2. Проверьте схему ответа до использования поля. Не полагайтесь на поле, которое приходит в ответе, но отсутствует в опубликованной схеме.
3. Используйте legacy endpoint `/backend/ax/...`, только если нужной функции нет в документированном API и PILOT подтвердил поддержку endpoint для расширений.
4. Укажите в документации расширения версию PILOT, endpoint, метод, способ авторизации, поля ответа и известные ограничения.

Список объектов API v3 может содержать runtime-данные, которых нет в OpenAPI-схеме. Считайте такие поля наблюдениями, пока спецификация API их не опишет.

## Настройки расширения в PILOT

`Pilot.Extensions.getSettings(name, scope)` — документированный host runtime API в сборках PILOT, где есть класс `Pilot.Extensions`.

Метод использует текущую авторизованную сессию PILOT. PILOT определяет текущий аккаунт и проверяет доступ к расширению. Метод не принимает ID аккаунта.

Область `effective` используется по умолчанию. Она объединяет глобальные настройки с настройками текущего аккаунта. Значения аккаунта заменяют глобальные значения с теми же ключами. Область `account` возвращает только настройки текущего аккаунта. Область `global` возвращает только глобальные настройки. Если в выбранной области нет значений, метод возвращает пустой объект.

Используйте JavaScript-метод. Не вызывайте его legacy endpoint `/backend/ax/pilotstore/list.php` напрямую. Метод отклоняет Promise, если сессия не авторизована, аккаунт не имеет доступа к расширению или параметры запроса некорректны.

Значения, переданные в браузер, видны его пользователям. Не храните в этих настройках пароли, приватные ключи и другие секреты. Для секретов используйте серверный backend расширения.

## Аутентификация и права

Интерфейсы PILOT могут использовать разные способы авторизации. Не предполагайте, что один формат токена подходит для всех endpoint’ов.

- Для документированных API endpoint следуйте разделу авторизации в спецификации API.
- Не используйте идентификатор браузерной сессии как универсальный API-токен.
- Не считайте, что same-origin URL `/store/<extension>/...` обеспечивает аутентификацию или проверку прав.
- Проверяйте права в backend расширения для данных, к которым пользователь не должен иметь доступ.
- Считайте `global_conf`, `CurrentUser`, role ID, списки модулей и подобные runtime-значения неподдерживаемыми для контроля доступа, пока PILOT не опишет их как стабильный API расширений.
- Различайте ошибку аутентификации и ошибку прав. Обычно `401` означает, что запрос не прошёл аутентификацию. Обычно `403` означает, что у аутентифицированного пользователя нет права. Точное поведение проверяйте в контракте endpoint.

Не используйте внутренний формат WebSocket-сообщений как API расширения. Для текущих или исторических данных используйте документированный endpoint. Если подходящего endpoint нет, запросите его у PILOT.

## Объём запросов и опрос данных

Не описывайте наблюдаемую частоту запросов как формальный лимит PILOT. Используйте опубликованный лимит, только если его задаёт контракт API или владелец установки.

Если лимит не опубликован:

- запрашивайте только изменившиеся данные;
- кэшируйте повторно используемые ответы;
- делите большие задачи на пакеты;
- распределяйте запросы по времени и объектам;
- повторяйте временные ошибки с увеличением паузы;
- прекращайте повторы при ошибках аутентификации и прав, пока не изменятся учётные данные или доступ.

Лимиты могут отличаться для разных endpoint’ов и установок. Правило сервера для одной группы URL не определяет лимит для остальных endpoint’ов.

## Значение и время данных

Для каждого отображаемого показателя укажите источник, единицы измерения, расчёт, период, фильтры и известную задержку. Имена полей и типы берите из схемы API. Бизнес-смысл уточняйте по документации продукта или подтверждённому определению данных.

Всегда указывайте часовой пояс параметров даты и времени. Не выводите часовой пояс аккаунта из часов браузера или сервера. Уточняйте, описывает ли ответ текущее состояние, историю событий или агрегат.

Не называйте показатель очищенным или проверенным, если источник не выполняет нужную проверку. Агрегат может сохранять аномалии, которые есть во входных данных.

## Обработка ошибок

| Ответ | Действие по умолчанию |
|---|---|
| `401` | Проверьте, переданы ли для этого endpoint действительные учётные данные. Не повторяйте запрос с теми же данными. |
| `403` | Проверьте права пользователя и доступ аккаунта. Не считайте автоматически, что модуль аккаунта отключён. |
| `429` | Снизьте частоту запросов. Если ответ содержит задержку повтора, соблюдайте её. |
| `500` | Запишите время и идентификатор запроса, затем сообщите об ошибке сервера. Не представляйте её как ошибку прав. |

Endpoint может задавать более точное поведение ошибок. Используйте его описание, если оно есть.

## Данные для сообщения о проблеме

Добавьте в запрос поддержки:

1. Версию PILOT и домен установки.
2. Endpoint, HTTP-метод и время запроса с часовым поясом.
3. Очищенные от секретов параметры запроса и тело ответа.
4. HTTP-статус и идентификатор запроса, если он есть.
5. Роль пользователя и соответствующие права. Не отправляйте пароли, cookie, идентификаторы сессий или bearer-токены.
6. Число объектов, диапазон дат, частоту запросов и настройки кэша.
7. Возникает ли та же ошибка в интерфейсе PILOT.

Удаляйте имена клиентов, ID аккаунтов, ID объектов и учётные данные из примеров для публичной документации.

## Проверка версии

При смене целевого выпуска PILOT проверьте спецификацию API и справочник runtime расширения. Проверьте примеры с host-классами, методами карты, глобальными переменными, legacy endpoint’ами и полями ответа без описания в схеме. Обновляйте сведения о совместимости только после проверки целевой сборки.
